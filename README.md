# OnePay

OnePay is an original, responsive fintech demo with real OnePay account authentication and **simulated payment activity**. It does not connect to a bank, UPI network, or payment provider, and it never moves real money. Never enter or store a real banking PIN, password, OTP, or card security code.

Account registration, sign-in, profile name updates, sign-out, and password reset are handled by the Django API. Server-side sessions use HttpOnly cookies with CSRF protection; the `Secure` cookie flag is enabled for HTTPS deployments by default. The frontend does not store authentication tokens or financial data in browser storage. Wallet balances, recipients, transaction history, ledger entries, receipts, and notifications are stored and validated by the backend. Display preferences remain session-only.

## Development setup

### 1. Start PostgreSQL and the backend

Use Python 3.11 or newer and PostgreSQL 16. From a terminal:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit `backend/.env` before starting the service. Replace `DJANGO_SECRET_KEY` with a unique value generated by:

```bash
python -c "import secrets; print(secrets.token_urlsafe(50))"
```

Choose a local PostgreSQL password and use the same value for `POSTGRES_PASSWORD` and the password in `DATABASE_URL`. With Docker Compose available, start the database from the `backend` directory:

```bash
docker compose up -d db
```

If you already run PostgreSQL locally, create a database/user matching `.env` instead. Then apply all account and payments migrations, create an administrative account if desired, and start Django:

```bash
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver 0.0.0.0:8000
```

The local `.env.example` uses Django's console email backend. Password-reset links for local accounts are printed in the backend terminal. For delivery, set `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, the `EMAIL_HOST`/`EMAIL_PORT`, and provider-issued `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/TLS values in the untracked `.env`; also set a public `FRONTEND_BASE_URL`. DRF authentication throttles use Django's cache: the default local-memory cache is appropriate for this single-process demo, while multi-worker deployments should configure a shared cache backend through `DJANGO_CACHE_BACKEND` and `DJANGO_CACHE_LOCATION`. For example, PostgreSQL's Django database-cache backend can share throttle state; set `DJANGO_CACHE_BACKEND=django.core.cache.backends.db.DatabaseCache`, `DJANGO_CACHE_LOCATION=django_cache`, then run `.venv/bin/python manage.py createcachetable django_cache` once. Never use the example secret or database password outside local development.

### 2. Start the frontend

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Vite listens on `0.0.0.0:5173` and proxies `/api` requests to `http://127.0.0.1:8000`, so browser code uses same-origin relative API URLs. To use another backend address, set `VITE_API_PROXY_TARGET` in the frontend environment. For a direct cross-origin deployment, explicitly configure `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` in the backend environment and serve the app over HTTPS.

The backend environment template includes the local frontend origins and the Arena preview-origin pattern for CSRF. Keep `DJANGO_ALLOWED_HOSTS`, CORS origins, and CSRF trusted origins limited to the domains actually used by your deployment.

## Authentication API

Base path: `/api/v1/auth/`

- `GET csrf/` — issue a CSRF cookie and return the token for the current page session
- `POST register/` — create a OnePay account and establish a session
- `POST login/` and `POST logout/` — sign in and invalidate the session
- `GET me/` and `PATCH profile/` — read the authenticated account and update its display name
- `POST password-reset/` and `POST password-reset/confirm/` — request a non-enumerating reset email and consume its one-time link

Unsafe requests require CSRF tokens. Protected endpoints require a valid Django session. Registration, login, and password reset use server-side validation and scoped rate limits. Do not add banking PINs, OTPs, bank passwords, card security codes, or real payment details to this demo.

## Simulated payments and ledger API

Base path: `/api/v1/payments/`. Every endpoint requires the authenticated Django session; unsafe requests also require the CSRF header. Amounts are integer INR paise (`amount_minor`), and the server fixes currency to `INR`. The browser never supplies an authoritative balance.

| Endpoint | Purpose |
| --- | --- |
| `GET wallet/` | Read the authenticated user's balance and currency. A first request creates a server-side demo wallet with ₹24,580.00 and an opening ledger entry. |
| `GET recipients/`, `POST recipients/` | List or add private demo contacts. Only built-in sample handles and mock `@onepay` / `@mock` identifiers are accepted. |
| `GET recipients/lookup/?identifier=...` | Resolve an owned recipient ID or supported mock UPI ID; verified OnePay account IDs resolve to the account's backend profile. No external UPI directory is queried. |
| `GET recipients/{id}/`, `PATCH recipients/{id}/`, `DELETE recipients/{id}/` | Read, edit, or soft-delete an authenticated user's own contact. |
| `POST qr/generate/` | Generate a signed INR demo QR for the authenticated OnePay account; the server supplies the account ID and profile name. |
| `POST qr/resolve/` | Validate the exact OnePay QR format and server signature, then return the backend-verified recipient profile. |
| `GET transactions/?limit=50` | Backward-compatible list of the authenticated user's latest transactions (limit 1–100). |
| `GET transactions/history/` | Paginated, account-scoped history; accepts `page`, `page_size` (1–50), `search`, `status`, `category`, `direction`, `date_from`, `date_to`, `min_amount_minor`, and `max_amount_minor`. The response includes result count, page metadata, and matching entries. |
| `POST transactions/` | Initiate a transfer, bill payment, or recharge through the existing transaction engine. Transfers may use an owned `recipient_id`, supported `upi_id`, or signed `qr_content`. Bill/recharge requests use a supported `service`, `provider`, and validated `recipient_reference`; optional `plan_code` values are checked against the fictional mock plan catalogue. Requires an `Idempotency-Key` header. |
| `GET transactions/{reference}/` | Read transaction details and status history, scoped to its sender. |
| `GET transactions/{reference}/status/` | Read the current status and timestamps. |
| `GET transactions/{reference}/receipt/` | Return the transaction details and an explicit simulated-receipt notice. |
| `POST transactions/{reference}/reverse/` | Legacy customer route; always returns HTTP 403. Reversals are not available through the customer API. |
| `POST wallet/topups/` | Add one of the allowed fictional wallet amounts (₹100, ₹250, ₹500, ₹1,000, or ₹2,500). Requires an `Idempotency-Key`. |

Example transfer request:

```http
POST /api/v1/payments/transactions/
Idempotency-Key: 4dd8a752-a620-4c39-9f43-eaa0f7aaf18d
Content-Type: application/json

{"kind":"transfer","recipient_id":1,"amount_minor":12500,"note":"Lunch"}
```

A transfer can use an owned `recipient_id`, supported `upi_id`, or the raw signed `qr_content` (exactly one is allowed). OnePay QR payloads use the `onepay://pay` scheme and include only the account's supported OnePay identifier, INR/demo/version fields, and a server HMAC; altered, unsupported, malformed, or unknown account identifiers are rejected both during resolution and again at payment initiation. The QR generator never accepts a client-supplied display name or arbitrary account identifier. Bill/recharge requests use `kind` (`bill` or `recharge`), a supported `service`, `amount_minor`, a supported mock `provider`, and a validated `recipient_reference`. Mobile references accept a 10-digit demo number (optionally prefixed by `+91`); other subscriber references must be 4–24 alphanumeric/hyphen characters. The backend stores a masked ending only, plus an irreversible private fingerprint for idempotency checks. Services include mobile, DTH, electricity, water, gas, broadband, and an additional mock utility category. Mock plan codes are validated against the selected mock operator and amount; the sample values and labels are fictional illustrations, not current provider offers, account quotes, or benefits. Payment amounts must be positive and cannot exceed ₹50,000. Recipients and all transaction/status/receipt/history queries are owner-scoped. Reusing an idempotency key with the same request returns the original transaction; using it for a different request returns HTTP 409. Receipt endpoints include an explicit simulation notice and reference number.

The scanner requests camera access only after the user selects **Start camera**. If access is denied or unavailable, the same screen supports manual entry of a OnePay demo ID or saved recipient ID. A scan performs backend QR/profile validation but never initiates a payment; the verified recipient and amount are reviewed first, and the user must explicitly confirm. Cancelling the review creates no transaction. The optional browser Contacts Picker is displayed only when supported and is opened only after an explicit click; selected details are prefilled for review and are not saved until the user submits the recipient form. Manual entry remains available in all browsers.

The backend records sender/recipient snapshots, a unique `OPW-…` reference, INR amount, timestamps, status history, audit events, and signed wallet-ledger entries. Wallet updates, transaction creation, and ledger writes occur atomically. Production databases use user/wallet row locks (`select_for_update`) to serialize balance operations; the SQLite test configuration adds an in-process per-user lock because SQLite ignores row locks. Check constraints prevent negative balances, and unique ledger/idempotency constraints prevent repeated debits or credits.

Supported transaction states are `pending`, `successful`, `failed`, and `reversed`. The local processor is deterministic and contacts no service: ordinary mock handles succeed; `fail@onepay` (or `decline@onepay`) demonstrates transfer failure/refund; `pending@onepay` (or `timeout@mock`) demonstrates a processor outage/pending state. For bill/recharge references, an identifier ending in `0000` demonstrates a local failure/refund, while one ending in `9999` demonstrates a local pending outcome; the full identifier is not stored. A retry with the same idempotency key can safely replay or resume a simulated operation. Persistent in-app notifications are generated from transaction-status events, wallet top-ups, bill/recharge outcomes, recipient changes, successful sign-ins, actual profile-name changes, and password resets. A transaction notification links to its account-scoped detail page; a deleted transaction is safely unlinked. QR generation or verification alone does not send a notification. Payment and recipient-change notices participate in the same database transaction as their source transition, so rollback removes both. Sign-in/profile/password notices are attempted only after their respective successful handler transition. Event keys make creation idempotent, and notification insert failures are contained so they do not turn a successful source operation into a failure. Top-ups are fictional ledger credits only. No real UPI transfer, bank lookup, biller call, carrier plan lookup, provider confirmation, or money collection is made, and the UI/API never request a UPI PIN, OTP, password, or card security code.

## Persistent in-app notifications

Base path: `/api/v1/notifications/`. Every operation requires the authenticated OnePay session and unsafe methods require CSRF. Notification rows and per-user read/dismiss state are stored in the backend database; the unread count is fetched after authentication and the full inbox is loaded when the notifications page is opened or refreshed. Notification data is not stored in browser storage. App-event rows are owned by one user. A system announcement is stored once and its read/dismiss state is kept separately per user. Queries and mutations enforce ownership on the server.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/v1/notifications/?page=1&page_size=20` | List the caller's active notifications and system announcements, newest first. Optional filters: `category`, `read=true|false`, `date_from`, `date_to` (`YYYY-MM-DD`), and `include_dismissed=true`. Page sizes are limited to 50. |
| `GET /api/v1/notifications/unread-count/` | Return `{ "unread_count": n }`, excluding dismissed records. |
| `POST /api/v1/notifications/{uuid}/read/` | Persist the caller's read state for one owned or broadcast notification. |
| `POST /api/v1/notifications/read-all/` | Mark all currently active notifications read for the caller. |
| `POST /api/v1/notifications/{uuid}/dismiss/` | Persist the caller's dismissal without modifying the shared announcement or another user's state. |
| `POST /api/v1/notifications/dismiss-all/` | Dismiss all active notifications for the caller. Dismissed items can be queried with `include_dismissed=true`. |

Supported event coverage is intentionally limited to actual OnePay workflows: outbound transfer success/failure and a real simulated pending outcome or internal reversal; successful simulated wallet top-ups; bill and recharge success/failure/pending outcomes; recipient creation, changed details, and removal; successful password sign-in, account display-name change, and password reset. QR creation, scanning, or verification by itself is not a payment and creates no notification. There is no incoming-funds workflow, failed top-up record, background settlement worker, email, push, or WebSocket delivery in this project; these are not fabricated. If an existing pending transaction is later settled on an idempotent retry, the new status event creates its own notification.

An active Django administrator, or an active staff account with the `notifications.add_notification` permission, can publish a system announcement using **Notifications → Add notification**; the admin forces the broadcast category/event and provides no recipient field. The `create_system_announcement()` service enforces the same permission. Announcement creation is audit-logged. There is deliberately no public create/broadcast endpoint. Only existing OnePay internal routes are accepted as navigation targets; invalid or stale transaction links are returned without a target.

## Phase 7: intelligent spending analysis

The `/insights` workspace turns the simulated payment ledger into an explainable spending review. It is implemented inside the existing `apps.analytics` application and reads the existing `PaymentTransaction` records; no payment, wallet, or notification behaviour is replaced.

- **Overview** — completed outflow, average daily spending, largest expense, top category, month-over-month comparison, category donut, daily and monthly trends, weekday/weekend averages, merchant totals, budget progress, recent evidence-backed insights, and a searchable/filterable transaction table with category drill-down.
- **Patterns** — deterministic observations (category concentration, frequent small payments, recurring payments, trend direction, unusual expenses relative to the user's own prior 180 days, category growth, and review opportunities). Every card exposes its evidence, baseline, calculation, confidence/data sufficiency, and a suggested next step. Forecasts use moving averages with an observed-range band and are withheld until 60 days of history, 10 completed payments, and 2 complete months exist. Anomalies require at least 10 prior payments.
- **Monthly report** — a plain-language executive summary, category and merchant totals, largest transactions, recurring payments, budget performance, unusual payments, savings opportunities, a six-month trend, and a CSV export generated from the same stored aggregates. Income remains explicitly unavailable because OnePay does not record verified incoming funds; demo top-ups are reported separately and are never counted as income.
- **Budgets and goals** — optional overall and per-category monthly limits with 80% and 100% warnings, previous-month comparison, calculated (labelled **Estimate**) recommendations only after two complete months and ten payments, and user-recorded savings goals. Transfers, refunds, pending, failed, reversed, and top-up records never count as consumption.
- **Categorization** — 18 categories with subcategories, driven first by persisted user corrections, then local merchant/description rules, payment metadata, an optional configured local classifier, and an optional LLM fallback. External AI is disabled by default, requires deployment configuration plus explicit user consent, and receives only a digit-masked merchant label, payment kind, and amount band. The categorization method and a rule-strength confidence are returned for every payment; saved corrections can apply to one payment or future matching merchants.
- **Privacy and correctness** — all endpoints are authenticated and owner-scoped. Amounts are integer paise and INR-only; date boundaries use Asia/Kolkata local midnight. Failed, pending, reversed, internal-transfer, and demo top-up records are excluded from completed spending. No bank balance or unrecorded income is inferred, and no sensitive transaction text is written to logs.

Analytics API (all under `/api/v1/analytics/`): `summary/`, `transactions/`, `categories/`, `trends/`, `merchants/`, `insights/`, `forecast/`, `anomalies/`, `reports/months/`, `reports/<year>/<month>/`, `reports/<year>/<month>/export.csv`, `budgets/`, `budgets/<id>/`, `goals/`, `goals/<id>/`, `transactions/<reference>/category/`, `corrections/`, `preferences/`, and `meta/`.

For a populated local demonstration:

```bash
cd backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_analytics_demo
```

The command creates `demo@onepay.test` / `OnePay!Demo2026` with four months of simulated payments, category budgets, and a savings goal. It is idempotent by default; pass `--force` to replace the generated demo activity. Cache entries are derived from the user's transaction/budget revision, so new or corrected records invalidate them automatically.

Run `manage.py check --deploy` against the actual deployment settings and review its conditional security warnings before release.

## Phase 6: security operations and API reference

- `GET /api/schema/` serves the OpenAPI 3 JSON description. It is public and rate-limited like other anonymous API requests. Unsafe API requests continue to require the server-side session and CSRF token; payment writes also use the `Idempotency-Key` header.
- `GET /health/live/` reports process liveness. `GET /health/ready/` checks database readiness. Both return only a generic status and disclose no connection details.
- Application responses carry an `X-Request-ID`. API errors include the same ID in the JSON `error.request_id` field. Unexpected API failures return a generic message and, when the database is available, are recorded with route, status, error class, and request ID only; request bodies, query strings, exception messages, and tracebacks are not serialized into application logs. If the database is unavailable, the audit row cannot be persisted and only the structured log remains.
- `/admin/dashboard/` provides user totals, simulated ledger/status metrics, recent API errors and local simulator pending/refund outcomes, and read-only transaction investigation. `/admin/audit/` is the append-only audit review. Both require active staff status and either superuser status or all of `accounts.view_user`, `payments.view_paymenttransaction`, `payments.view_auditevent`, `payments.view_transactionstatushistory`, and `payments.view_walletledgerentry`. Django admin payment, ledger, recipient, status-history, and audit models are read-only; admin access and privileged user/announcement changes are audit-logged. Staff accounts cannot grant themselves staff/superuser permissions through the user-admin form.
- Transaction records must start `pending`; status changes go through the atomic transition service, which writes a constrained, append-only status-history row. Database constraints validate transaction kinds/statuses, INR-only ledger values, ledger sign, unique idempotency keys, and valid status transitions. Existing wallet/idempotency behavior remains simulated and backend-owned.
- Internal reversal retries must reuse the original reversal idempotency key. Replaying that key returns the original reversed transaction; a different key for an already-reversed transaction returns a conflict and does not create another ledger credit.

These are application-level safeguards and test evidence for this demo, not a claim of PCI DSS, RBI, banking, or other regulatory compliance. Production still requires infrastructure controls, operational monitoring, backups, incident response, access review, and an independent security assessment.

# OnePay

OnePay is an original, responsive fintech demo with real OnePay account authentication and **simulated payment activity**. It does not connect to a bank, UPI network, or payment provider, and it never moves real money. Never enter or store a real banking PIN, password, OTP, or card security code.

Account registration, sign-in, profile name updates, sign-out, and password reset are handled by the Django API. Server-side sessions use HttpOnly cookies with CSRF protection; the `Secure` cookie flag is enabled for HTTPS deployments by default. The frontend does not store authentication tokens or financial data in browser storage. Demo balances, transactions, preferences, and UPI-format examples remain in memory and reset when the page is reloaded.

## Development setup

### 1. Start PostgreSQL and the backend

Use Python 3.11 or newer and PostgreSQL 16. From a terminal:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit `backend/.env` before starting the service. Replace `DJANGO_SECRET_KEY` with a unique value generated by:

```bash
python -c "import secrets; print(secrets.token_urlsafe(50))"
```

Choose a local PostgreSQL password and use the same value for `POSTGRES_PASSWORD` and the password in `DATABASE_URL`. With Docker Compose available, start the database from the `backend` directory:

```bash
docker compose up -d db
```

If you already run PostgreSQL locally, create a database/user matching `.env` instead. Then apply the initial custom-user migration, create an administrative account if desired, and start Django:

```bash
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver 0.0.0.0:8000
```

The local `.env.example` uses Django's console email backend. Password-reset links for local accounts are printed in the backend terminal. For delivery, set `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, the `EMAIL_HOST`/`EMAIL_PORT`, and provider-issued `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/TLS values in the untracked `.env`; also set a public `FRONTEND_BASE_URL`. DRF authentication throttles use Django's cache: the default local-memory cache is appropriate for this single-process demo, while multi-worker deployments should configure a shared cache backend through `DJANGO_CACHE_BACKEND` and `DJANGO_CACHE_LOCATION`. For example, PostgreSQL's Django database-cache backend can share throttle state; set `DJANGO_CACHE_BACKEND=django.core.cache.backends.db.DatabaseCache`, `DJANGO_CACHE_LOCATION=django_cache`, then run `.venv/bin/python manage.py createcachetable django_cache` once. Never use the example secret or database password outside local development.

### 2. Start the frontend

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Vite listens on `0.0.0.0:5173` and proxies `/api` requests to `http://127.0.0.1:8000`, so browser code uses same-origin relative API URLs. To use another backend address, set `VITE_API_PROXY_TARGET` in the frontend environment. For a direct cross-origin deployment, explicitly configure `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` in the backend environment and serve the app over HTTPS.

The backend environment template includes the local frontend origins and the Arena preview-origin pattern for CSRF. Keep `DJANGO_ALLOWED_HOSTS`, CORS origins, and CSRF trusted origins limited to the domains actually used by your deployment.

## Authentication API

Base path: `/api/v1/auth/`

- `GET csrf/` — issue a CSRF cookie and return the token for the current page session
- `POST register/` — create a OnePay account and establish a session
- `POST login/` and `POST logout/` — sign in and invalidate the session
- `GET me/` and `PATCH profile/` — read the authenticated account and update its display name
- `POST password-reset/` and `POST password-reset/confirm/` — request a non-enumerating reset email and consume its one-time link

Unsafe requests require CSRF tokens. Protected endpoints require a valid Django session. Registration, login, and password reset use server-side validation and scoped rate limits. Do not add banking PINs, OTPs, bank passwords, card security codes, or real payment details to this demo.

## Checks

Frontend:

```bash
cd frontend
npm run typecheck
npm test
npm run build
```

Backend (SQLite in-memory for the automated suite; this does not replace a PostgreSQL deployment check):

```bash
cd backend
DJANGO_DEBUG=true DJANGO_SECRET_KEY='test-only-local-key' DATABASE_URL='sqlite:///:memory:' .venv/bin/python manage.py check
DJANGO_DEBUG=true DJANGO_SECRET_KEY='test-only-local-key' DATABASE_URL='sqlite:///:memory:' .venv/bin/python manage.py makemigrations --check --dry-run
DJANGO_DEBUG=true DJANGO_SECRET_KEY='test-only-local-key' DATABASE_URL='sqlite:///:memory:' .venv/bin/pytest -q
```

For production, set a strong `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=false`, exact `DJANGO_ALLOWED_HOSTS`, HTTPS-only `COOKIE_SECURE=true`, and appropriate `SECURE_SSL_REDIRECT`, HSTS, CORS, CSRF, email, and PostgreSQL settings. Set `TRUST_PROXY_SSL_HEADER=true` only when a trusted reverse proxy removes incoming forwarded-protocol headers and sets `X-Forwarded-Proto` itself. Review these settings with the deployment's trusted-proxy and cookie-domain configuration before release.
